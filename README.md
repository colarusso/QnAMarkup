# QnA Markup — client-side edition

[QnA Markup](https://www.qnamarkup.org/) turns structured text into an interactive
question-and-answer session. This is a pure JavaScript implementation of the
interpreter plus a new editor: no server-side code, so a QnA can be hosted on
any static host or dropped into an existing page with two `<script>` tags.

```html
<script src="https://www.qnamarkup.org/dist/2.1.0/qna.min.js"></script>
<script type="text/qna">
Q: Would you like to embed a QnA?
A: Yes.
	Q: Then you already have.
A: No.
	Q: Fair enough.
</script>
```

That's the whole thing. The library finds every `<script type="text/qna">`,
parses the markup and renders the conversation right where the tag sits.

## What's in the box

| --- | --- |

| `dist/qna.js` | Same, unminified and commented. |

| `src/qna.js` | Source. `dist/` is generated from it by `build.js`. |
| `index.html`, `editor.js` | The editor (Markup / Settings tabs, templates, resizable panes, Interactive / Link / Embed Code / HTML full page / Flowchart outputs). The script is a separate file so the page can be served with a strict Content-Security-Policy. |

## Hosting

The site runs on two domains: `https://www.qnamarkup.org` serves the editor,
docs and the library, and `https://www.qnamarkup.net` serves the viewer and
the document page, so QnAs (which may contain anybody's JavaScript) never run
on the editor's origin. Both are plain static hosts. `DEPLOY.md` has the whole
procedure: `./deploy.sh` builds `site/org/` and `site/net/` and rsyncs each to
its server, and the server headers (CORS on `dist/` for SRI, long caching for
versioned copies, a CSP on the editor origin) and redirects for old links are
listed there.

Every release of the library is published at
`https://www.qnamarkup.org/dist/<version>/qna.min.js` and never changed
afterwards; the editor writes that URL, with an `integrity` hash, into embed
code. `dist/qna.min.js` (unversioned) is the latest build.

To host your own copy, set `editorOrigin` and `viewerOrigin` at the top of
`config.js` (they may be the same origin if you accept the trade-off) and
deploy. Everything also works from `file://` and from a single `localhost`
port for development, except fetching remote `?source=` files from `file://`.

## Embedding options

Style options go on the markup element as `data-` attributes. The names match
the editor's Settings tab (camelCase or the original snake_case both work):

```html
<script type="text/qna"
        data-font-family="Georgia, serif" data-font-size="16" data-line-height="24"
        data-col-width="600" data-frame-pad="15" data-radius="15"
        data-comp-bg="336699" data-comp-txt="ffffff" data-comp-link="e3fbfc"
        data-usr-bg="eeeeee" data-usr-txt="000000" data-usr-link="0000ff"
        data-body-bg="ffffff" data-body-txt="000000" data-body-link="0000ff"
        data-chat-style="sms" data-label-back="GO BACK ONE" data-label-restart="START OVER"
        data-footer="false" data-start="1" data-target="#render-here">
…
</script>
```

* `data-chat-style` — `sms` (the default: questions and answers in speech
  bubbles) or `llm`: questions are set straight on the page like a chat
  assistant's replies. In `llm`, `question_text` takes the Body Colors
  (`data-comp-bg`, `data-comp-txt` and `data-comp-link` are accepted but not
  used, so the editor can keep them for a switch back to `sms`), has no
  padding, margin or border radius apart from 8px of padding on top,
  `question_arrow` is hidden, and `ans_text` gets an 8px top margin.
* `data-label-save`, `data-label-back`, `data-label-restart` — the text of the
  built-in buttons ("Save above text as answer.", "GO BACK ONE", "START OVER").
  `data-label-credits`, `data-label-edit`, `data-label-code` — the text of the
  footer links ("credits", "edit", "code your own"). Plain text, not HTML; up
  to 200 characters; blank means the standard wording.
* `data-body-bg`, `data-body-txt`, `data-body-link` — the "Body Colors": the
  background behind the conversation (and of the whole page in the viewer /
  full-page outputs, which carry `<body class="qna-page">`), and the colour of
  text and links outside the bubbles (Before/After content, footer). The
  credits box always sits on grey, so it keeps black text and standard link
  colours. The Body Text font family, size and line height apply to the whole
  body, credits included.
* `data-target` — CSS selector of the element to render into (default: a new
  `<div class="qna">` inserted right after the markup element).
* `data-footer="false"` — hide the credits / edit / code-your-own footer.
* `data-start` — id of the question to start at.
* `data-editor-url` — where the footer's *edit* and *code your own* links go.
* `data-save-progress="true"` — remember the visitor's answers in their browser
  (localStorage) and resume where they left off next time; *Start over* clears it.
  Off by default, and when it is off the runtime stores nothing at all: answers
  live only in the page until it is closed. The saved answers are keyed on the
  markup, so a changed QnA never restores stale answers.
* `data-load-timeout` — ms to wait for a question's images before showing it
  anyway (default 30000). While waiting, a typing indicator (three dots) is
  shown. Images that fail resolve immediately, so this only guards against
  requests that hang; slow hosts can take 10+ seconds for a large GIF.

The markup lives in a `<script type="text/qna">` tag because browsers leave
the contents of a script tag exactly as written (tabs, HTML and all). The one
sequence that cannot appear inside it is a closing `</script>`; write it as
`<\/script>` (the editor's Embed Code and HTML outputs do this for you, and
the library turns it back before parsing).

### The hidden `Settings:` tag

The editor's *Save to File* appends one last line to the saved text,
`Settings: fontSize=18; compBg=336699; …`, holding the Settings screen. *Load
File* strips it and restores those settings. The parser removes it (only as
the last non-blank line) before anything else and returns its values as
`parse().settings`; when such a file is rendered, they style the QnA unless
the same option is given as a `data-` attribute or passed to `QnA.render`,
which wins. `QnA.splitSettings(markup)` and `QnA.settingsTag(options)` do the
splitting and writing. Pairs are separated by semicolons, so inside the text of
a label (`labelBack=…`) a `;` is written `%3B` and a `%` `%25`.

### Scripts in a QnA

`<script>` tags written in the markup run, wherever they appear:

```
Before: <script>
function greet(name) { return 'Hello, ' + name + '!'; }
</script>

Q(name): What is your name?
X:
	Q: <span id="hi"></span>
	<script>document.getElementById('hi').textContent = greet(JSON.parse(json_str()).name);</script>
	A[javascript:alert(greet('again'));]: Say it again
```

* They run as ordinary page scripts in the global scope, so a function defined
  in `Before:` can be called from an `A[javascript:…]` button, from a later
  script, and from the page the QnA is embedded in.
* They run in the order written. An external script (`<script src="…">`)
  holds back the scripts after it until it has loaded (or failed), so a
  library can be loaded in `Before:` and used straight away.
* `Before:` and `After:` scripts run once per render, when the QnA's frame is
  in the page but before the first question is drawn. A script in a `Q` runs
  each time its bubble is drawn, which includes the redraw after *GO BACK* and
  when saved progress is restored (`QnA.current.replaying` is `true` then).
* An `X` tag can carry code too: `X[javascript:…]:` or `X:[javascript:…]` (either
  side of the colon, no difference; several lines allowed, as for `A`). It runs
  after the visitor's text has been saved to the question's variable, on Enter
  or the button, and not on a redraw. The bracket must hold `javascript:` code:
  the parser reports empty brackets or a missing prefix as errors.
* A script can find its QnA with `QnA.current`, or, with several QnAs on a
  page, `document.currentScript.closest('.qna').qna`.
* Script tags with a non-JavaScript `type` (JSON, templates) are left alone.
  Script and style blocks are left out of transcripts and flowchart boxes.
* The editor's preview reloads its sandboxed frame before re-rendering a QnA
  whose scripts have run, so each render starts from a clean page, as a
  published QnA does.

### Programmatic use

```js
QnA.render(element, markup, options)   // -> instance (or null if the markup has errors; errors are rendered)
QnA.parse(markup)                       // -> { ok, errors, code, header, questions, answers, names }
QnA.css(options)                        // -> the CSS string the runtime injects
QnA.encodeHash({ markup, ...options })  // -> Promise<string>  "z=…" fragment used by share links
QnA.decodeHash(fragmentOrQuery)         // -> Promise<{ markup, ...options }>
QnA.init(scope)                         // render any not-yet-rendered markup elements under scope
```

`parse().code` is the markup with computed ids filled in (`Q(1.1):`), which is
what the editor writes back into the text area when you click *Update Outputs*.

Set `window.QNA_NO_AUTOINIT = true` before loading the library, or add
`data-auto="false"` to its script tag, to disable automatic rendering.

### Predefined functions

All of the original helpers are available as globals, so existing QnAs with
`A[javascript:…]` buttons keep working: `transcript(format)`, `doc()`,
`json_str()`, `mail2(to, subject, body)`, `save2(filename, content)`,
`submit2(action, method, docAs, instructions, transcriptAs, jsonAs, target)`.
They are also namespaced under `QnA.*`, and a page that already defines a
global of the same name keeps its own.

A `[javascript:…]` bracket may span several lines, so scripts can be written
readably; each line is trimmed and `//` comments are dropped before the code
runs. A literal `]` inside any bracket is written `\]`:

```
A[javascript:
  // build a summary and show it
  var s = transcript();
  alert("Answers so far:\n" + s);
]: Show me a summary.
```

The bundled `doc/` page is the CKEditor-based document editor. Because it is a
static page it can only read the document from the URL, so send it with `GET`:
`submit2('https://www.qnamarkup.net/doc/', 'GET', 't', 'instructions')`.
(`submit2` with `POST` still works against any server of your own.) It loads
CKEditor 4.22.1, the last open-source release of CKEditor 4; later 4.x releases
are commercially licensed, and `config.js` has a slot for a licence key if you
have one. There is also a lightweight in-page alternative, **`showdoc(instructions)`**,
which opens the document in an editable overlay with Print / Save / Copy buttons
without leaving the QnA.

## Differences from the PHP implementation

The parser was ported line by line and checked against the original with a
PHP oracle (`test/compare.js` runs both over every template, every example on
the syntax page, a set of edge cases and — when present locally — 31 real QnAs from the gallery). The
markup produced, ids assigned, answers, variables and error conditions match,
with these deliberate exceptions:

1. **GOTO renumbering works.** The docs promised that a GOTO would follow its
   target when ids were renumbered; the PHP code for that was unreachable, so a
   stale `GOTO:1.3` silently pointed at the wrong question after a re-render.
   Numeric targets are now remapped along with their questions.
2. **GOTO targets are also checked against computed ids.** `Q:` … `GOTO:1`
   is accepted even before the editor has written `Q(1):` into the text.
3. **`A():` gives an empty answer value**, as the documentation's Santa example
   relies on. (The PHP fell back to the button text.)
4. **GOTO targets containing capital letters are validated** — the PHP's
   pre-check was case-sensitive and let a broken `GOTO:Not` through to fail at
   runtime.
5. Header tags are parsed correctly when text (e.g. a comment) precedes them;
   `\r\n` line endings are normalised; a duplicate-name error is reported once.
6. **Spaces work as indentation, not just tabs.** Nesting is structural: what
   matters is that tags at the same level line up, so 2-space, 4-space or tab
   indentation all work (a tab counts as 4 columns when mixed with spaces). A
   tag indented deeper than the previous one is one level deeper however much
   whitespace it uses, and a dedent that lines up with no earlier tag is
   reported as an error. (The PHP recognised only tabs and treated
   space-indented tags as plain text; one QnA in the gallery was written that
   way and now parses as its author intended.)

The rendered HTML keeps the same structure, ids and class names
(`#conversation`, `#QandA`, `#Choices`, `.question_text`, `.qabutton`, …) and
the same generated CSS, so custom styling written for the old output still
applies. "Go back one" now replays the conversation from its history rather
than editing the DOM with regular expressions, which also means the variable
of an undone answer is cleared.

Old share links of the form `i/?markup=…&font_size=…&sharing=2` continue to
work in the new viewer, and the editor's Link output can still produce that
plain-text form. The default, compressed form packs the QnA into the URL
fragment (`i/#z=…`), which holds far more than the old 4,000-character limit.
The viewer also accepts raw URL-encoded markup after the `#`, with or without
a `markup=` key.

## Development

```
npm install            # esbuild (minifier) and playwright (browser tests)
npm run build          # dist/ + templates/templates.js
npm run templates      # regenerate templates/templates.js only (after editing templates/*.txt)
npm run watch          # rebuild whenever src/ or templates/ changes
npm run serve          # dev server at http://localhost:8000/ (editor) and /i/ (viewer)
node test/compare.js   # parser vs. the original PHP (needs php on PATH)
node test/runtime.js   # runtime behaviour in headless Chromium
node test/e2e.js       # editor + viewer end to end
```

The build fails if any template has markup errors, and warns about media
referenced over `http://`.

### What is (and isn't) in the repository

Everything here is safe to publish. `dist/` is committed so the built library
can be fetched straight from GitHub or mirrored by a CDN. `test/oracle/` is a
copy of the original PHP interpreter (also MIT, from this project), lightly
patched to run under PHP 8 from the command line. `test/corpus/` — real QnAs
from the gallery, written by their own authors — is deliberately excluded by
`.gitignore`; the comparison test runs without it. Nothing in the tree holds
keys, credentials or personal data; `config.js` has an empty slot for a
CKEditor licence key, which should stay empty in the public copy.
